# User Journey: от запроса на специалиста до отправки CV клиенту

## Важное замечание по структуре

Процесс **сильно варьируется** от компании к компании. Роли, каналы передачи запроса и наличие отдельных этапов (например, технического апрува) — не универсальны. Документ описывает все возможные варианты; конкретная реализация настраивается под компанию.

---

## Участники процесса

Состав участников зависит от структуры компании. Возможные роли:

| Роль | Зона ответственности | Наличие |
|---|---|---|
| **HR-специалист / рекрутер** | Поиск по скамье, оценка, координация, упаковка CV | Всегда |
| **Инициатор запроса** | Источник потребности в специалисте | Всегда; роль варьируется |
| **Технический апрувер** | Оценка соответствия кандидата | Опционально |
| **Ответственный за отправку** | Передача профиля клиенту | Всегда; может быть HR или другой человек |
| **Сотрудник (кандидат)** | Подтверждение готовности | Всегда |

### Варианты роли «Инициатор запроса»

Запрос может приходить от разных источников — в зависимости от структуры компании:

- **Аккаунт-менеджер** — от существующего клиента, с которым уже есть отношения
- **Сейлз** — от нового клиента в процессе продажи
- **Сам клиент** — напрямую, если настроен прямой канал коммуникации
- **Внутренний запрос** — потребность закрыть роль на собственный проект компании

### Варианты канала передачи запроса HR

Нет единого стандарта. Встречаются:

- Мессенджер (Slack, Telegram) — наиболее частый вариант
- Email
- Устно / звонок
- Заполненная форма / шаблон брифа
- Задача в трекере (Jira, Notion, Trello)

> ⚠️ Боль: отсутствие единого канала и формата приводит к тому, что информация теряется, HR приходится уточнять одно и то же снова и снова.

## Этап 1. Появление запроса

### 1.1 Инициатор формирует потребность

**Типичные триггеры:**
- Клиент расширяет команду под новый модуль или фазу проекта
- Уход текущего специалиста с проекта
- Рост объёма задач
- Начало нового проекта / продажа новому клиенту
- Внутренняя потребность компании

**Что обычно известно на этом этапе:**
- Общее описание задачи («нужен бэкенд-разработчик»)
- Примерные сроки старта
- Иногда стек и грейд, иногда нет

> ⚠️ Боль: запрос редко приходит в структурированном виде. Чем менее формализован процесс передачи — тем больше времени уходит на уточнения.

---

### 1.2 Формирование внутреннего брифа

Прежде чем HR начнёт поиск, необходимо собрать полный бриф. Кто это делает — зависит от структуры компании: это может быть инициатор запроса, HR, или они делают это совместно.

**Обязательные параметры брифа:**

```
├── Специализация и роль — Frontend / Backend / Fullstack / DevOps / QA / …
├── Стек — конкретные технологии и версии (React 18, Node.js 20, PostgreSQL)
├── Грейд — Junior / Middle / Senior / Lead
├── Загрузка — full-time / part-time, количество часов в день
├── Часовой пояс — локация клиента и минимальный overlap
├── Дата старта — ASAP / конкретная дата / гибко
├── Длительность — 3 мес / 6 мес / ongoing / неизвестно
└── Бюджет / ставка — диапазон или фиксированная цифра
```

**Желательные параметры:**

```
├── Домен проекта — fintech, e-com, healthtech, SaaS, …
├── Уровень английского — письменный / устный, частота общения с клиентом
├── Автономность — насколько самостоятельно нужно работать
├── Размер и состав команды клиента
└── Специфические требования — конкретный опыт, сертификаты, отраслевая экспертиза
```

**Если бриф неполный** → HR возвращается к инициатору с уточнениями. Это может занять от 30 минут до нескольких часов.

---

### 1.3 HR фиксирует запрос как активную вакансию

Создаётся карточка вакансии:
- Название позиции
- Источник запроса (клиент / инициатор)
- Полный список требований из брифа
- Дата получения запроса
- Дедлайн — когда ожидаются первые профили
- Приоритет — срочно / стандартно
- Статус: **Новая**

---

## Этап 2. Поиск по скамье

### 2.1 Первичная фильтрация базы

HR просматривает базу сотрудников и применяет жёсткие фильтры:

```
Фильтр 1: Статус сотрудника
└── "На скамье" ИЛИ "Освобождается до [дата старта + буфер 1 неделя]"

Фильтр 2: Ключевые технологии
└── Совпадение ключевого стека (не обязательно 100%)

Фильтр 3: Грейд
└── Запрошенный ±1 уровень

Фильтр 4: Доступная загрузка
└── Есть ли нужное количество часов?

Фильтр 5: Часовой пояс
└── Возможен ли достаточный overlap с клиентом?
```

**Результат:** шортлист 3–15 человек для ручной оценки

> ⚠️ Боль: данные о стеке сотрудников часто устаревшие — человек полгода работал с новым стеком, а в базе старые технологии. Статус «на скамье» может не обновляться вовремя.

---

### 2.2 Ручная оценка шортлиста

HR открывает профиль каждого кандидата и смотрит глубже:

**Технический профиль:**
- Реальный опыт с нужным стеком — не просто тег, а конкретные проекты
- Насколько последний проект близок к домену клиента?
- Сложность решаемых задач
- Насколько давно и плотно работал с ключевыми технологиями?

**История взаимодействий с клиентами:**
- Был ли уже представлен этому клиенту ранее? → повторная отправка без весомой причины недопустима
- Какие фидбеки давали прошлые клиенты?
- Были ли проблемы с коммуникацией, дедлайнами, качеством?

**Личные флаги:**
- Отказывался ли от похожих проектов раньше?
- Есть ли планы (отпуск, переезд, личные обстоятельства)?
- Ведутся ли параллельные переговоры по другой позиции?

**Результат:** топ 2–4 кандидата

> ⚠️ Боль: информация разрозненная — часть в базе, часть в голове коллег, часть в переписке. HR собирает картину вручную из нескольких источников.

## Этап 3. Технический апрув (опционально)

> **Этот этап может отсутствовать.** В небольших компаниях HR принимает решение самостоятельно или совместно с руководителем. В других — обязателен апрув технического специалиста.

### Если этап присутствует:

**Кто может быть апрувером:**
- CTO / технический директор
- Тимлид направления
- Старший разработчик, знакомый с кандидатом

**Что передаётся апруверу:**
- Шортлист 2–4 кандидатов
- Краткое обоснование по каждому
- Конкретный вопрос: «Этот человек потянет данный стек и сложность?»

**Возможные решения:**
- ✅ Одобрен — готов к следующему шагу
- 🔄 Нужна внутренняя проверка — быстрое техинтервью или тестовое
- ❌ Не подходит — причина фиксируется, HR ищет дальше

> ⚠️ Боль: апрувер занят текущими задачами. Ожидание ответа — от нескольких часов до 1–2 дней. Это главное бутылочное горлышко там, где этап существует.

### Если этапа нет:

HR самостоятельно принимает решение на основе профиля и истории сотрудника, либо решение принимается совместно с инициатором запроса.

---

## Этап 4. Проверка готовности сотрудника

### 4.1 HR связывается с кандидатом

**Это обязательный шаг перед любой отправкой.**

Формат: звонок или сообщение — важно получить живую реакцию, а не формальное «да».

**Что уточняется:**

```
Готовность к проекту:
├── Знаешь ли об этой возможности? Как относишься в целом?
├── Готов стартовать [дата]?
└── Есть ли что-то, что может помешать?

Мотивация:
├── Интересен ли домен / стек?
├── Устраивает ли формат (часы, таймзона, тип задач)?
└── Что сейчас важно для тебя в проекте?

Условия:
├── Зарплатные ожидания изменились?
├── Есть ли другие предложения, которые рассматриваешь?
└── Есть ли планы в ближайшее время (отпуск, переезд)?
```

**Варианты ответа:**
- ✅ Готов и мотивирован → движемся дальше
- 🟡 Готов с оговорками → уточняем детали, принимаем решение
- ❌ Не готов или не хочет → следующий кандидат из шортлиста

> ⚠️ Боль: если пропустить этот шаг — клиент одобряет кандидата, а тот в последний момент отказывается. Это репутационный риск для компании.

### 4.2 Фиксация договорённости

После подтверждения HR фиксирует:
- Сотрудник уведомлён и согласен
- Дата старта согласована
- Ожидания по условиям записаны
- Статус: **Согласован для отправки**

---

## Этап 5. Подготовка CV под клиента

### 5.1 Сбор исходного материала

- Актуальное резюме сотрудника
- Описания проектов из базы
- Оценка уровня английского
- Фото (если требуется шаблоном)

### 5.2 Адаптация резюме под конкретного клиента

Резюме не копируется — оно **переупаковывается** под запрос:

```
├── Акцент на релевантный опыт
│   └── Проекты, близкие к домену клиента — в начало
│
├── Сокращение нерелевантного
│   └── Технологии и проекты, не относящиеся к запросу — убираются или сокращаются
│
├── Переформулировка под контекст клиента
│   └── Язык описания задач адаптируется под домен клиента
│
├── Языковая адаптация
│   └── Перевод / вычитка на нужный язык (EN, DE, и т.д.)
│
├── Оформление в шаблон компании
│   └── Фирменный стиль, структура, логотип (если принято)
│
└── Анонимизация (если принято в компании)
    └── Имя заменяется на инициалы или убирается до момента оффера
```

### 5.3 Сопроводительный питч (опционально)

Короткий текст (5–10 строк), который идёт вместе с CV:
- Почему именно этот человек под этот запрос
- Что в его опыте наиболее релевантно
- Готовность к старту, ключевые условия

### 5.4 Финальная проверка перед отправкой

```
Чеклист:
├── Фактические ошибки? (даты, стек, названия компаний)
├── Соответствует требованиям клиента?
├── Не отправлялся ли этот профиль этому клиенту ранее?
├── Технический апрув получен? (если этап есть)
└── Сотрудник уведомлён и готов?
```

**Статус: Готов к отправке**

> ⚠️ Боль: CV переделывается вручную под каждого клиента. Нет шаблонизации, нет истории версий. Непонятно, какой вариант CV кому и когда отправлялся.

---

## Этап 6. Передача ответственному за отправку

Кто отправляет профиль клиенту — зависит от структуры:
- HR отправляет напрямую (если есть прямой контакт с клиентом)
- Инициатор запроса (AM / сейлз) — наиболее частый вариант
- Руководитель компании

**Что передаётся:**
- Готовое CV в нужном формате (PDF / DOCX)
- Сопроводительный питч (если есть)
- Контекст: готовность к старту, ключевые условия, на что обратить внимание

**Статус в базе: Отправлен клиенту** — дата и время фиксируются

## Итоговая схема journey (базовый вариант)

```
[ИНИЦИАТОР ЗАПРОСА]
Появляется потребность в специалисте
            │
            ▼
[ИНИЦИАТОР / HR]
Сбор и формирование брифа
            │
            ▼  ──── Неполный бриф ────▶ Уточнение
            │
[HR]
Фиксация вакансии в базе
            │
            ▼
[HR]
Фильтрация базы скамьи
(статус + стек + грейд + загрузка + таймзона)
            │
            ▼  ──── Никого нет ────────▶ Внешний поиск (другой процесс)
            │
[HR]
Ручная оценка шортлиста
Отбор топ 2–4 кандидатов
            │
            ▼
[ОПЦИОНАЛЬНО: технический апрув]
            │  ──── Нужна проверка ───▶ Внутреннее техинтервью
            │  ──── Все отклонены ────▶ HR ищет снова
            │
[HR → СОТРУДНИК]
Проверка готовности
            │
            ▼  ──── Не готов ─────────▶ Следующий кандидат
            │
[HR]
Подготовка CV под клиента
Финальная проверка пакета
            │
            ▼
[HR → ОТВЕТСТВЕННЫЙ ЗА ОТПРАВКУ]
Передача пакета
            │
            ▼
Профиль отправлен клиенту ✅
```

## Что должно настраиваться в системе

Исходя из вариативности процесса, следующие параметры должны быть конфигурируемыми:

| Параметр | Варианты |
|---|---|
| Кто является источником запроса | AM / Сейлз / Клиент напрямую / Внутренний |
| Канал получения запроса | Форма в системе / Мессенджер / Email / Задача |
| Нужен ли технический апрув | Да / Нет |
| Кто апрувит технически | CTO / Тимлид / Старший разработчик |
| Кто отправляет профиль клиенту | HR / AM / Руководитель |
| Формат CV для клиента | Шаблон компании / Оригинальное резюме |
| Анонимизация до оффера | Да / Нет |
| Обязательность питча | Да / Нет |

## Узкие места и точки автоматизации

| Этап | Боль | Что можно автоматизировать |
|---|---|---|
| Передача запроса | Нет единого формата, данные теряются | Структурированная форма брифа с обязательными полями |
| Фиксация вакансии | Делается вручную, статусы не обновляются | Автосоздание карточки вакансии из брифа |
| Фильтрация базы | Устаревшие данные о стеке и статусе | Актуальный профиль сотрудника, авто-фильтрация |
| Ручная оценка | Информация в разных местах | Единая карточка с историей, фидбеками, статусами |
| Технический апрув | Долгое ожидание, нет дедлайна | Уведомления, таймаут, async-форма апрува |
| Проверка готовности | Шаг пропускается | Обязательный чеклист, блокировка следующего шага |
| Подготовка CV | Ручная переделка каждый раз | Шаблоны, конструктор CV, история версий |
| Проверка перед отправкой | Не знают историю отправок | Журнал: кому / когда / какой профиль отправлялся |
| Передача пакета | Теряется контекст | Автоматически сформированный пакет с нужной информацией |

## Временные ориентиры

| Этап | Время (норма) | Время (с задержками) |
|---|---|---|
| Сбор и уточнение брифа | 1–2 часа | до 1 дня |
| Фильтрация базы | 30–60 минут | — |
| Ручная оценка шортлиста | 1–3 часа | до 4 часов |
| Технический апрув (если есть) | 2–4 часа | до 1–2 дней |
| Проверка готовности сотрудника | 30–60 минут | до 4 часов |
| Подготовка CV (1 профиль) | 1–2 часа | до 4 часов |
| **Итого от запроса до отправки** | **1–2 дня** | **3–5 дней** |
