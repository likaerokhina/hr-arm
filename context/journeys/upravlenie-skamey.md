# User Journey: управление скамьёй сотрудников

## Контекст

Скамья — это не просто список свободных людей. Это живая база, от актуальности которой зависит качество всего подбора. Если данные устарели — ИИ-матчинг выдаёт нерелевантные результаты, HR тратит время на ручную проверку, клиент получает несоответствующие профили.

Вся ответственность за базу лежит на **HR-специалисте и аккаунт-менеджере** — сотрудники не имеют доступа к системе и не участвуют в ведении своих профилей.

---

## Участники

| Роль | Зона ответственности |
|---|---|
| **HR-специалист** | Создаёт и ведёт профили, управляет статусами, поддерживает актуальность базы |
| **Аккаунт-менеджер** | Фиксирует фидбеки от клиентов, обновляет статусы по итогам переговоров |
| **Система (ИИ)** | Напоминает об обновлениях, валидирует данные, автоматически меняет статусы |

---

## Структура профиля сотрудника

```
ПРОФИЛЬ СОТРУДНИКА
│
├── 📋 БАЗОВАЯ ИНФОРМАЦИЯ
│   ├── Имя, контакты, фото
│   ├── Роль / специализация (Frontend, Backend, DevOps…)
│   ├── Грейд (с датой последней оценки)
│   ├── Локация и часовой пояс
│   └── Уровень английского (с датой последнего подтверждения)
│
├── ⚙️ ТЕХНИЧЕСКИЙ СТЕК
│   ├── Технологии с уровнем владения и датой последнего использования
│   ├── Must-have (основной стек)
│   ├── Nice-to-have (знает, но не основной)
│   └── В процессе изучения
│
├── 🗂️ ПРОЕКТНЫЙ ОПЫТ
│   ├── Каждый проект: домен, стек, роль, длительность, результат
│   ├── Текущий проект (если есть)
│   └── Хронология проектов в компании
│
├── 📊 СТАТУС И ДОСТУПНОСТЬ
│   ├── Текущий статус (см. ниже)
│   ├── Процент занятости (0% / 50% / 100%)
│   ├── Дата освобождения (точная или прогнозируемая)
│   └── Известные периоды недоступности
│
├── 🤝 ИСТОРИЯ ВЗАИМОДЕЙСТВИЙ С КЛИЕНТАМИ
│   ├── Кому и когда отправлялся профиль
│   ├── Результат каждой отправки
│   └── Причины отказов (со стороны клиента и со стороны сотрудника)
│
└── ⭐ ФИДБЕКИ И ОЦЕНКИ
    ├── Фидбеки от клиентов после проектов
    ├── Внутренние оценки (грейд, динамика роста)
    └── Результаты технических проверок
```

## Journey 1: Создание профиля нового сотрудника

### Триггер
Новый человек выходит на работу в компанию.

### Шаг 1.1 — HR создаёт карточку

HR заполняет базовые данные вручную:
- Имя, контакты, специализация
- Грейд (со слов и на основе резюме)
- Локация и часовой пояс
- Уровень английского

Статус автоматически: **«Онбординг»** — в пул скамьи не попадает.

### Шаг 1.2 — HR заполняет технический стек

На основе резюме и собеседования HR вносит стек:

```
ИИ помогает при вводе:
→ Стандартизирует названия технологий
   («ReactJS» → «React», «Postgres» → «PostgreSQL»)
→ Предлагает указать уровень для каждой технологии:
   [ Базовый ]  [ Уверенный ]  [ Продвинутый ]  [ Эксперт ]
→ Запрашивает дату последнего коммерческого использования
→ Предлагает смежные технологии для проверки
   («Указан React — добавить TypeScript, Redux?»)
```

### Шаг 1.3 — HR вносит проектный опыт

По каждому проекту из резюме HR заполняет карточку проекта:

```
Структура карточки проекта:
├── Домен / индустрия (fintech, e-com, healthtech…)
├── Стек, который использовался на проекте
├── Роль сотрудника
├── Длительность участия
├── Краткое описание задач
└── Источник: до компании / внутри компании
```

ИИ на основе введённых данных автоматически формирует описание проекта для CV — HR только проверяет.

### Шаг 1.4 — Профиль активируется

HR переводит статус вручную: **«Онбординг» → «На скамье»**

После этого:
- Профиль становится доступен для поиска и скоринга
- ИИ помечает поля с датой — через 3 месяца придёт напоминание об обновлении

## Journey 2: Поддержание актуальности профиля

### 2.1 — Плановые обновления по расписанию

Система автоматически создаёт задачи для HR:

```
Каждые 3 месяца:
→ «Обнови стек [Имя] — актуальны ли технологии?
   Последнее обновление: [дата]»

Каждые 6 месяцев:
→ «Проверь уровень английского [Имя]»
→ «Уточни зарплатные ожидания [Имя]»

Каждые 12 месяцев:
→ «Обнови фото профиля [Имя]»
→ Полный аудит профиля
```

### 2.2 — Событийные обновления

HR обновляет профиль при конкретных событиях:

**Сотрудник освоил новую технологию или получил сертификат:**
```
HR добавляет в стек:
→ Технология, уровень владения, дата
→ ИИ предлагает смежные технологии на проверку
→ Статус технологии: «Подтверждено сертификатом» / «Со слов»
```

**Сотрудник работает с новой технологией на текущем проекте:**
```
HR или AM отмечает в профиле:
→ Технология добавляется со статусом «В активном использовании»
→ Дата последнего использования обновляется
→ ИИ через 3 месяца предложит повысить уровень владения
```

### 2.3 — ИИ-валидация актуальности

ИИ постоянно анализирует профили и создаёт задачи для HR:

```
⚠️ Примеры автоматических предупреждений:

«[Имя] — технология [X] не использовалась более 12 месяцев.
Рекомендуем понизить статус с "основной" до "знает, но не активно".»

«[Имя] — уровень английского не подтверждался 9 месяцев.
Уточните актуальность перед следующей отправкой.»

«[Имя] — грейд Senior, но последняя внутренняя оценка была 11 месяцев назад.
Рекомендуем обновить оценку.»

«[Имя] — трижды отказывался от проектов с таймзоной EST.
Рекомендуем добавить ограничение в предпочтения.»
```

## Journey 3: Управление статусами сотрудника

Это самый критичный journey — точность статусов определяет качество фильтрации скамьи.

### Возможные статусы

```
На скамье          — полностью свободен, доступен для проектов
Частично свободен  — есть частичная загрузка, доступен part-time
На проекте         — полностью занят
На рассмотрении    — профиль отправлен, ждём решения клиента
Оффер              — клиент одобрил, идут переговоры
Пауза по проекту   — проект временно заморожен
Недоступен         — отпуск, больничный, личные обстоятельства
Онбординг          — новый сотрудник, не в пуле
```

### 3.1 — Сотрудник выходит на проект

**Кто меняет:** HR или AM после подтверждения старта

```
Действия HR:
├── Статус: «На скамье» → «На проекте»
├── Занятость: указать % (100% / 50% / 20%…)
├── Дата старта: [дата]
├── Прогнозируемая дата окончания: [дата]
├── Клиент: привязка к карточке клиента
└── Стек на этом проекте: что будет использоваться

Автоматически:
→ Сотрудник исчезает из пула скамьи
→ ИИ ставит напоминание за 2 недели до даты окончания
→ В истории проектов создаётся новая запись
```

### 3.2 — Проект заканчивается или ставится на паузу

**Триггер А: плановое завершение**

```
За 2 недели до даты окончания ИИ создаёт задачу для AM:
«Проект [Имя] заканчивается [дата]. Уточните у клиента:
продление / завершение / пауза?»

AM фиксирует результат:
→ Завершён → HR меняет статус на «На скамье»
→ Продлён → HR обновляет дату окончания
→ Пауза → HR меняет статус на «Пауза по проекту» + дата возобновления
```

**Триггер Б: досрочное завершение**

```
AM или HR меняет статус вручную:
→ Статус → «На скамье» (немедленно)
→ Указывается причина: клиент отказался / проект закрыт / другое
→ Причина фиксируется для аналитики
```

**Триггер В: частичное освобождение**

```
Проект переходит в режим поддержки:
→ Занятость: 100% → 20%
→ Статус → «Частично свободен»
→ Сотрудник появляется в пуле для part-time запросов
```

### 3.3 — Сотрудник недоступен (отпуск, больничный)

```
HR отмечает период недоступности:
→ Статус → «Недоступен»
→ Даты: с [дата] по [дата]
→ При фильтрации скамьи период автоматически исключается

За 2 дня до возвращения:
→ ИИ уведомляет HR: «[Имя] выходит [дата]»
→ HR подтверждает и возвращает предыдущий статус
```

### 3.4 — Сотрудник на рассмотрении у клиента

Промежуточный статус — часто теряется без системы:

```
После отправки профиля клиенту (автоматически):
→ Статус → «На рассмотрении: [Клиент]»
→ Дата отправки: [дата]
→ Ожидаемый ответ: [дата, если известна]

ИИ отслеживает:
→ Нет ответа N дней → задача AM: «Запроси фидбек у клиента»

Исходы:
→ Клиент одобрил → AM меняет статус на «Оффер»
→ Клиент отказал → HR возвращает «На скамье» + фиксирует причину
→ Отказ от сотрудника → HR возвращает «На скамье» + фиксирует причину
```

## Journey 4: Сбор фидбеков

### 4.1 — Фидбек от клиента после завершения проекта

**Триггер:** проект завершён, статус сотрудника изменился на «На скамье»

```
Через 3–5 дней ИИ создаёт задачу для AM:
«Получи фидбек от [Клиент] по работе [Имя]»

AM собирает фидбек и заносит в систему:
├── Общая оценка (1–5)
├── Качество результата
├── Коммуникация и самостоятельность
├── Соблюдение сроков
├── Оценка уровня английского клиентом
├── Готов ли клиент снова работать с этим человеком? (да / нет / возможно)
└── Свободный комментарий
```

ИИ анализирует фидбек и обновляет профиль:

```
→ Клиент отметил сильный английский → уровень подтверждается
→ Повторный паттерн «задержки с дедлайнами» → внутренний флаг для HR
→ «Хотим снова» → фиксируется как приоритетный для данного клиента
→ Технический отказ → предупреждение при следующем матчинге
```

### 4.2 — Фиксация причин отказов

**Клиент отклонил кандидата:**
```
AM фиксирует причину в карточке:
[ Не подошёл технически ]
[ Недостаточный уровень английского ]
[ Нашли другого кандидата ]
[ Проект отменён / заморожен ]
[ Другое: _____ ]
```

**Сотрудник отказался сам:**
```
HR фиксирует причину:
[ Не интересен домен ]
[ Не устраивает таймзона ]
[ Условия не совпали ]
[ Личные обстоятельства ]
[ Другое: _____ ]

ИИ обновляет предпочтения в профиле автоматически:
→ При повторном матчинге учитывает паттерн отказов
→ Предупреждает HR: «[Имя] уже дважды отказывался от EST-таймзоны»
```

## Journey 5: Мониторинг всей скамьи

### 5.1 — Дашборд скамьи (ежедневный взгляд HR)

```
СКАМЬЯ — сегодня

Свободны прямо сейчас:           8 чел.
Освобождаются в ближайшие 2 нед: 3 чел.
На рассмотрении у клиентов:      4 чел.
Частично свободны (part-time):   5 чел.

⚠️ Требуют внимания:
→ [Имя] — на скамье 23 дня, нет активных переговоров
→ [Имя] — профиль не обновлялся 4 месяца
→ [Имя] — проект заканчивается через 5 дней, статус не подтверждён
→ [Имя] — ожидаем фидбек от клиента уже 8 дней
```

### 5.2 — Прогноз освобождений

```
ПРОГНОЗ НА 60 ДНЕЙ

Неделя 1–2:
→ [Имя] — Senior React, освобождается [дата], контракт заканчивается
→ [Имя] — Backend Python, возвращается из отпуска [дата]

Неделя 3–4:
→ [Имя] — Fullstack, проект → поддержка, будет 20% занятости

Неделя 5–8:
→ [Имя] — DevOps, контракт предположительно не продлят (флаг от AM)
→ [Имя] — QA, плановое завершение

⚡ Рекомендация ИИ:
Начать проактивный поиск проектов под [Имя] уже сейчас —
через 2 недели он будет на скамье, а pipeline пустой.
```

### 5.3 — Аудит качества базы

ИИ автоматически раз в неделю формирует отчёт для HR:

```
АУДИТ БАЗЫ — [дата]

Профилей всего:                    47
Неполные профили:                   8  → [список + что именно отсутствует]
Устаревший стек (>6 мес):           5  → [список]
Без фидбеков от клиентов:          12  → [список]
Статус не обновлялся >30 дней:      3  → [список]
Грейд не подтверждался >12 мес:     4  → [список]

Задачи на эту неделю (приоритет):
1. Обновить стек [Имя, Имя] — оба на активном поиске проекта
2. Запросить фидбек через AM по [Имя, Имя, Имя]
3. Уточнить дату окончания проекта у [Имя] — дата прошла неделю назад
```

## Правила целостности данных

```
1. Статус всегда определён
   → Нет статуса «неизвестно» или пустого поля
   → При каждом изменении фиксируется: кто изменил и когда

2. Дата освобождения обязательна
   → Если точная неизвестна — прогнозируемая с пометкой «~»
   → ИИ запрашивает подтверждение за 2 недели до даты

3. Стек имеет давность
   → Каждая технология — с датой последнего коммерческого использования
   → Через 12 месяцев без использования → автоматически помечается устаревшей

4. История отправок неизменяема
   → Нельзя удалить факт отправки профиля клиенту
   → Можно только добавить контекст и результат

5. Фидбеки хранятся навсегда
   → Даже негативные не удаляются — добавляется контекст
```

## Связь с ИИ-матчингом

| Данные в профиле | Как используется при подборе |
|---|---|
| Стек + дата последнего использования | Основа технического скоринга |
| Статус + дата освобождения | Фильтр доступности |
| % занятости | Фильтр по full-time / part-time |
| Часовой пояс | Фильтр overlap с клиентом |
| История отправок | Исключение повторных отправок тому же клиенту |
| Фидбеки клиентов | Бонус / штраф к итоговому скору |
| Причины отказов | Предупреждения и фильтрация нежелательных матчей |
| Грейд (дата оценки) | Фильтр и скоринг; старый грейд → предупреждение |
