# AI-автоматизированный Journey: от запроса до отправки CV

## Принцип подхода

Человек принимает решения. ИИ устраняет рутину, собирает контекст и готовит всё необходимое — чтобы каждый шаг занимал секунды, а не часы.

Три уровня автоматизации:
- 🤖 **Полная автоматизация** — ИИ делает сам, человек не участвует
- ⚡ **Ускорение** — ИИ готовит, человек проверяет и подтверждает одним кликом
- 🧠 **Поддержка решения** — ИИ даёт рекомендацию с объяснением, человек решает

---

## Этап 1. Получение и разбор запроса

### Было (без ИИ)
Инициатор пишет в мессенджер. HR читает, не понимает что не хватает, пишет обратно, ждёт ответа. Цикл уточнений занимает от часа до дня.

### Стало (с ИИ)

**1.1 Умная форма брифа** 🤖

Инициатор открывает форму запроса. ИИ задаёт уточняющие вопросы по мере заполнения — динамически, в зависимости от ответов:

```
Инициатор: "Нужен React-разработчик"
ИИ: "Уточните версию React и нужен ли TypeScript?"
Инициатор: "React 18, TypeScript обязателен"
ИИ: "Укажите грейд. Для вашего стека обычно важен опыт с
     state management — Redux, Zustand или MobX нужен?"
```

ИИ не даёт отправить бриф, пока не заполнены все обязательные поля.

**1.2 Автоматический разбор неструктурированного запроса** ⚡

Если запрос пришёл текстом из мессенджера — ИИ парсит его и сам заполняет поля брифа:

```
Входящее сообщение:
"Привет, клиент из Германии просит Senior React-разработчика,
желательно с опытом в fintech, старт через 2 недели,
работа full-time, они работают по CET"

Распознано ИИ:
├── Специализация: Frontend / React
├── Грейд: Senior
├── Домен: Fintech
├── Старт: [текущая дата + 14 дней]
├── Загрузка: Full-time (8 ч/день)
├── Часовой пояс клиента: CET (UTC+1)
└── Не заполнено: стек (версия?), ставка, длительность → запрос на уточнение
```

HR видит предзаполненную форму и только проверяет / дополняет пропуски.

**1.3 Автоматическая валидация реалистичности** 🤖

ИИ проверяет бриф на противоречия до того как HR начнёт поиск:

```
⚠️ Обнаружены потенциальные проблемы:
- Senior React + TypeScript в таймзоне CET — узкий пул на скамье (2 чел.)
- Указана ставка $X — ниже медианы для данного грейда на 20%
- Старт через 2 недели — текущий pipeline перегружен, риск задержки

Рекомендации:
→ Рассмотреть Strong Middle как альтернативу Senior
→ Уточнить у клиента гибкость по ставке
→ Поднять приоритет запроса
```

**Результат этапа:** структурированный бриф за 5–10 минут вместо 1–4 часов

---

## Этап 2. Фиксация вакансии

### Было
HR вручную создаёт карточку, копирует данные из брифа, присваивает статус.

### Стало (с ИИ)

**2.1 Автосоздание карточки вакансии** 🤖

После подтверждения брифа система автоматически:
- Создаёт карточку вакансии со всеми полями
- Присваивает уникальный ID
- Устанавливает дедлайн (дата старта клиента − 3 рабочих дня)
- Уведомляет HR о новой задаче
- Устанавливает приоритет на основе срочности и важности клиента

**2.2 Автоматический запуск поиска** 🤖

Сразу после создания карточки ИИ начинает фильтрацию — HR не нужно делать это вручную.

---

## Этап 3. Поиск и ранжирование по скамье

### Было
HR вручную фильтрует таблицу, открывает каждый профиль, держит всё в голове.

### Стало (с ИИ)

**3.1 Автоматическая фильтрация** 🤖

ИИ мгновенно применяет все фильтры по базе:
- Статус: на скамье / освобождается вовремя
- Стек: семантическое совпадение (не просто точное — «React» ≈ «ReactJS» ≈ «React 17/18»)
- Грейд, загрузка, таймзона

**3.2 Скоринг и ранжирование кандидатов** 🧠

ИИ выдаёт не просто список, а ранжированный шортлист с объяснением по каждому:

```
┌─────────────────────────────────────────────────────────┐
│ #1 Алексей К.  ████████████ 94/100                      │
│                                                          │
│ ✅ React 18 + TypeScript — 2 года активного опыта       │
│ ✅ Fintech-проект (Payments, 18 мес) — прямое попадание  │
│ ✅ CET overlap — 6 часов, норма                         │
│ ✅ Доступен с [дата] — за 3 дня до старта клиента       │
│ ⚠️ Redux не упомянут — уточнить при проверке готовности │
│ ℹ️ Последний клиент оставил положительный фидбек        │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│ #2 Марина В.   ████████░░░░ 78/100                      │
│                                                          │
│ ✅ React 18 + TypeScript — опыт есть                    │
│ ✅ Доступна с [дата] — точно в срок                     │
│ ⚠️ Fintech-опыта нет, но был e-commerce (похожая логика) │
│ ⚠️ CET overlap — 4 часа, минимально допустимо           │
│ ℹ️ Ранее отказывалась от немецких клиентов — уточнить   │
└─────────────────────────────────────────────────────────┘
```

**3.3 Автоматические флаги истории** 🤖

ИИ автоматически помечает:
- 🚫 «Уже отправлялся этому клиенту [дата]» — блокировка повторной отправки
- ⚠️ «Отказывался от похожих проектов (2 раза)» — предупреждение
- ⚠️ «Параллельно рассматривается на другую позицию» — конфликт

**Результат этапа:** ранжированный шортлист с контекстом за секунды вместо 1–4 часов

## Этап 4. Технический апрув (если настроен)

### Было
HR пишет тимлиду в мессенджер. Тимлид занят. Ждём.

### Стало (с ИИ)

**4.1 ИИ готовит техническое резюме для апрувера** ⚡

Вместо того чтобы апрувер сам изучал профили, ИИ готовит компактную выжимку:

```
Запрос на технический апрув — [имя кандидата]

Позиция: Senior React Developer для [Клиент]
Стек: React 18, TypeScript, Zustand, REST API

Анализ соответствия:
├── React 18 + TypeScript: 2 года, 3 проекта — подтверждено
├── State management: Zustand упомянут в 1 проекте — уровень неясен
├── Fintech-опыт: есть (Payments система, 18 мес)
└── Сложность задач: судя по описаниям — middle-senior уровень

Вопрос для апрувера: достаточен ли уровень владения Zustand
для данного проекта, или нужна дополнительная проверка?

[✅ Одобрить]  [🔄 Нужна проверка]  [❌ Отклонить + причина]
```

Апрувер нажимает одну кнопку — не изучает профиль с нуля.

**4.2 Автодедлайн и эскалация** 🤖

Если апрувер не ответил в течение настроенного времени (например, 4 часа):
- Автоматическое напоминание
- Через 8 часов — уведомление руководителю
- Опция: HR может принять решение самостоятельно с пометкой «без технического апрува»

---

## Этап 5. Проверка готовности сотрудника

### Было
HR звонит / пишет сотруднику вручную. Иногда забывает. Иногда пропускает этот шаг.

### Стало (с ИИ)

**5.1 Автоматическое уведомление сотрудника** 🤖

После апрува система автоматически отправляет сотруднику уведомление:

```
Привет! Для тебя появилась возможность — проект [краткое описание].

Основное:
• Стек: React 18, TypeScript
• Домен: Fintech (платёжная система)
• Формат: Full-time, CET overlap
• Старт: [дата]
• Длительность: ~6 месяцев

Пожалуйста, ответь до [дедлайн — 4 часа]:

[✅ Интересно, готов обсудить]
[🟡 Интересно, но есть вопросы]
[❌ Сейчас не подходит]
```

**5.2 ИИ-обработка ответа** 🧠

- ✅ Готов → система автоматически переводит статус, уведомляет HR
- 🟡 Есть вопросы → HR получает уведомление, чтобы связаться лично
- ❌ Не готов → система автоматически предлагает следующего кандидата из шортлиста

**5.3 Автофиксация договорённостей** 🤖

После подтверждения в карточке автоматически фиксируется:
- Сотрудник уведомлён: ✅ [дата, время]
- Готовность подтверждена: ✅
- Статус обновлён: «Согласован для отправки»

---

## Этап 6. Подготовка CV

### Было
HR открывает Word, вручную копирует данные, адаптирует текст под клиента, переводит, форматирует. 1–2 часа на один профиль.

### Стало (с ИИ)

**6.1 Автогенерация CV под конкретного клиента** ⚡

ИИ генерирует адаптированное резюме автоматически на основе:
- Профиля сотрудника в базе
- Требований вакансии
- Домена клиента
- Настроенного шаблона компании

Что ИИ делает:

```
├── Выбирает релевантные проекты
│   └── Fintech-проекты — в начало; нерелевантные — сокращаются
│
├── Адаптирует описания
│   └── «Разработал модуль оплаты» →
│       «Разработал высоконагруженный платёжный модуль
│        с поддержкой 10k транзакций/сек» (если данные есть)
│
├── Выделяет точки совпадения со стеком вакансии
│   └── Технологии из требований — выделены или стоят первыми
│
├── Переводит на нужный язык
│   └── EN / DE / FR — с учётом профессионального контекста
│
└── Применяет шаблон компании
    └── Фирменный стиль, структура, анонимизация если нужно
```

HR получает готовый черновик — остаётся прочитать и при необходимости поправить детали.

**6.2 Автогенерация сопроводительного питча** ⚡

ИИ пишет короткий питч под клиента:

```
Черновик питча для [Клиент]:

Предлагаем Алексея — Senior React-разработчика с 4 годами опыта
и 18 месяцами работы в fintech (платёжные системы). Хорошо знает
TypeScript, имеет реальный опыт с высоконагруженными проектами.
Готов к старту [дата], full-time, CET overlap 6 часов.

[Редактировать]  [Принять]
```

**6.3 Финальный чеклист перед отправкой** 🤖

ИИ автоматически проверяет и показывает статус:

```
Проверка перед отправкой:

✅ Фактические данные проверены (даты, стек, названия)
✅ Соответствие требованиям: 94/100
✅ Этому клиенту ранее не отправлялся
✅ Технический апрув получен
✅ Сотрудник уведомлён и готов
⚠️ Английский не проверялся — рекомендуем уточнить уровень

[Отправить на следующий шаг]
```

Один клик — если всё ок.

**Результат этапа:** готовый адаптированный CV за 10–15 минут вместо 1–2 часов

---

## Этап 7. Передача и отправка

### Было
HR пересылает файл, объясняет контекст, тот кто отправляет — снова разбирается в деталях.

### Стало (с ИИ)

**7.1 Автоматически сформированный пакет** 🤖

Система собирает пакет для отправки:
- CV в нужном формате
- Сопроводительный питч
- Краткий бриф для отправителя: ключевые моменты, что подчеркнуть, возможные вопросы клиента

**7.2 ИИ-подсказки для отправителя** 🧠

```
💡 Контекст для разговора с клиентом:

Сильные стороны этого кандидата под данный проект:
→ Прямой fintech-опыт (редкость на рынке)
→ Свободен раньше, чем просил клиент

На что обратить внимание:
→ Zustand — уровень средний, клиент может спросить
→ Немецкий — нет, только английский

Если клиент спросит про [возможный вопрос]:
→ [рекомендуемый ответ на основе профиля]
```

**7.3 Автофиксация события** 🤖

После отправки система автоматически:
- Фиксирует: кому, когда, какой профиль отправлен
- Обновляет статус вакансии: «Отправлен клиенту»
- Обновляет статус сотрудника: «На рассмотрении у [Клиент]»
- Запускает таймер ожидания фидбека от клиента
- Ставит автонапоминание: если нет ответа через N дней → follow-up

```
│  Парсит запросы, задаёт уточняющие вопросы,            │

└─────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────┐
│                   MATCHING AGENT                        │
│  Фильтрует базу, скорит кандидатов, объясняет          │

                          │
                          ▼

                          │
                          ▼

```

## Где человек остаётся в контуре

ИИ не заменяет решения — он убирает рутину. Человек остаётся обязательным участником в следующих точках:

| Точка | Почему человек, не ИИ |
|---|---|
| Финальный выбор кандидатов из шортлиста | Интуиция, нюансы отношений, политика |
| Технический апрув (если настроен) | Ответственность за качество |
| Разговор с сотрудником при «🟡 есть вопросы» | Доверие, мотивация, человеческий контакт |
| Редактура CV и питча | Тон, нюансы, точность формулировок |
| Решение об эскалации или исключении | Контекст, которого нет в базе |

## Требования к данным для работы ИИ

Качество автоматизации напрямую зависит от качества данных о сотрудниках:

```
Профиль сотрудника должен содержать:
├── Актуальный стек с уровнями владения и датами
├── Описания проектов с доменом, стеком, ролью, длительностью
├── История отправок: кому / когда / результат
├── Фидбеки от прошлых клиентов
├── Уровень английского (подтверждённый)
├── Часовой пояс и предпочтения по формату работы
├── Текущий статус и точная дата освобождения
└── Личные флаги: отказы, предпочтения, ограничения
```

> Это означает, что ЛК должен не только автоматизировать процесс подбора, но и поддерживать актуальность профилей сотрудников — иначе ИИ будет работать на устаревших данных.
